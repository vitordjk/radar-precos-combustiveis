Três projetos, uma história

Cada projeto do portfólio responde a uma pergunta diferente do ciclo de decisão, na ordem em que uma empresa amadurece com dados: primeiro enxergar o que está acontecendo, depois garantir que o dado por trás disso é confiável e chega sozinho, por fim antecipar o que vem e recomendar o que fazer.

Nenhum repete o outro: mudam o domínio de negócio, a arquitetura e as ferramentas, de propósito.

PROJETO 01 Descritivo e distribuição

Aurora Alimentos

O que está acontecendo no negócio, e quem precisa saber já sabe?

Operação completa de BI para uma indústria de laticínios fictícia: banco PostgreSQL com 3,4 milhões de linhas simuladas (30 distribuidores, 250 lojas, 48 produtos, 18 meses de movimento), modelo estrela com visões materializadas, painel em Power BI e um sistema de alertas em Python que envia por e-mail, para cada audiência, apenas o que ela precisa decidir.

  • Cobertura de estoque calculada de forma ponderada, não por média simples: no caso base, a diferença é 9,4 contra 15,2 dias, suficiente para inverter uma decisão de compra.
  • Estimador de risco de ruptura validado contra a simulação, com erro medido de 5,4% para menos.
  • Motor de sugestão de pedido e alertas segmentados para vendedor, gestor, diretor e reposição.

Pilha: PostgreSQL · Python · Power BI e DAX · HTML e CSS · SMTP

PROJETO 02 Engenharia e confiabilidade

Radar de Preços de Combustíveis

Como garantir que o dado que alimenta tudo é confiável e chega sozinho?

Plataforma de dados ponta a ponta sobre a Série Histórica de Preços da ANP: ingestão versionada com comparação por hash, arquitetura em camadas (bronze em Parquet, staging e marts em DuckDB via dbt), orquestração com Dagster e integração contínua que executa o pipeline inteiro a cada alteração no código.

  • 29 testes de qualidade em toda construção da base, com severidades deliberadas: erro bloqueia o pipeline, aviso pede investigação sem parar a operação.
  • Execução idempotente comprovada: rodar duas vezes não duplica nada, e a deduplicação entre fontes sobrepostas é determinística.
  • Sem testes verdes, sem merge: a integração contínua roda o pipeline completo contra dados de exemplo versionados.

Pilha: Python · DuckDB · dbt · Dagster · GitHub Actions · Parquet

PROJETO 03 Preditivo e prescritivo

Previsão de demanda e apoio à decisão

O que vai acontecer, e o que fazer a respeito?

Produto de dados que fecha o ciclo: previsão de demanda validada por backtesting temporal (o modelo só é aprovado se acertar em janelas que nunca viu), estimativa de elasticidade de preço e uma camada de otimização que transforma previsão em recomendação respeitando restrições reais do negócio.

  • Backtesting com janelas deslizantes no tempo, nunca validação aleatória: série temporal exige honestidade cronológica.
  • Elasticidade estimada por produto para responder o que acontece com a demanda quando o preço muda.
  • Interface de simulação para quem decide, com modelos versionados e comparáveis entre si.

Pilha: Python · Streamlit · MLflow · scikit-learn

Como eu trabalho

Número antes de adjetivo

Todo projeto entrega resultado medido: erro do estimador, taxa de exclusão da limpeza, diferença entre a métrica certa e a errada. Se não dá para medir, ainda não terminou.

A estatística certa é decisão de engenharia

Cobertura ponderada em vez de média simples, mediana em vez de média em preços com cauda. A escolha errada produz um painel bonito que induz a decisão errada.

Falhar de forma visível

Pipelines que quebram em silêncio custam caro. Meus projetos tratam erro e anomalia de formas diferentes e testam o próprio processo de limpeza, não só o dado.

Documentar a decisão, não só o código

Cada repositório registra as alternativas descartadas e o custo aceito. É o documento que eu gostaria de encontrar em todo projeto herdado.
